# 同步开发现场与文档

## 调用与宿主闸门

只接受以下两种入口证据：

- Claude Code：带 `disable-model-invocation: true` 的 `/sync:docs`
  薄入口已读取本文件、声明宿主并传入全部参数。
- Codex：本文件由 `allow_implicit_invocation: false` 的 `$sync:docs`
  或 `/skills` 显式选择直接加载。

若两种证据都不存在，停止并提示使用平台原生入口，禁止写项目文件。
不能根据已有指令文件猜宿主，禁止同时修改两套平台文件。

若调用参数含 `预览`，本次为只读运行：输出全部拟执行动作（含迁移计划与淘汰
明细），**禁止创建、修改或删除任何文件**。该闸门作用于下列全部步骤，先于
一切写入与删除判定——步骤 2 无论是执行淘汰决议中的删除、休眠标记，还是
执行迁移或写入三层，命中此闸门时一律只列入报告，不落盘。

## 定位项目根、主干与共享目录

若属于 Git 仓库，运行 `git rev-parse --show-toplevel` 并使用返回目录作为项目根；
否则使用当前工作目录。各 worktree 的项目根互不相同，这是分支现场天然隔离的基础。

协同看板位于 `git rev-parse --path-format=absolute --git-common-dir` 返回目录下的
`sync/lines/`。所有 worktree 的该路径指向同一个主仓库 `.git`，因此看板天然跨
worktree 共享，且不进 Git、不参与 merge。

主干分支按以下优先级探测，**禁止使用 `git config init.defaultBranch`**，其值可能
与真实主干不符：

1. `git symbolic-ref --quiet refs/remotes/origin/HEAD`，去掉 `refs/remotes/origin/` 前缀
2. `refs/remotes/origin/main` 或 `refs/remotes/origin/master` 的存在性
3. `refs/heads/main` 或 `refs/heads/master` 的存在性
4. 均不可得时，**跳过 merged 判据（tier 2）**，保留分支存在性判据与时间判据，
   并在报告中说明。只有 merged 判据需要主干，另外两条不需要，不得因主干探测
   失败就连带停掉整个孤儿回收

实时 Git、测试和文件状态优先于旧交接文档；旧交接只作为线索。发现冲突时写入当前
事实，并把未重新验证的旧结论标为未验证或删除。

## 三层交接布局

按变动频率与归属范围分为三层，各层职责不得混淆。

| 层 | 位置 | 进 Git | 内容 |
|---|---|---|---|
| 稳定层 | 项目根 `HANDOFF.md` | 是 | 概览、运行现状、配置项清单、重要文件、长期决策、坑、常用命令 |
| 分支现场 | `.handoff/<slug>-<hash>.md` | 是 | 任务看板、本分支决策、下一步 |
| 协同看板 | `<common-dir>/sync/lines/<slug>-<hash>.md` | 否 | 一句话状态、占用文件、最后更新时间 |

文件名生成规则：`slug` 为分支名把 `/ \ : * ? " < > |` 替换为 `-`；`hash` 为
**完整分支名的 UTF-8 字节**做 SHA-1 后取前 6 位十六进制小写。必须显式使用 UTF-8，
不得依赖平台默认编码，否则含中文的分支名在不同宿主下会算出不同哈希。加哈希是
必需的：`feat/auth` 与 `feat-auth` 的 slug 相同，仅靠 slug 会碰撞。

**当前分支名用 `git branch --show-current` 取得**，它输出不带 `refs/heads/` 前缀的
完整分支名，正是 `slug` 与 `hash` 的唯一输入（旧版 Git 可用等价的
`git symbolic-ref --quiet --short HEAD`）。**不要用 `git rev-parse --abbrev-ref HEAD`**：
处于游离 HEAD 时它输出字面量 `HEAD`，会被当成一个叫 `HEAD` 的分支名，据此算出的
文件名对应一条根本不存在的线。`git branch --show-current` 在游离 HEAD 时输出**空
字符串且 exit code 仍为 0**，因此判定游离 HEAD 要看**输出是否为空**，不能看 exit
code；此时按「游离 HEAD 的退化」处理。

**哈希必须用命令算出，禁止心算、目测或凭印象填写。** 语言模型无法可靠计算
SHA-1，一旦编造，每次调用都会得到不同的文件名：上一轮的现场文件立刻变成孤儿，
本轮又新建一个，下面的分支名一致性校验随即把整轮运行拦停。薄入口已声明 `Bash`
工具，按当前宿主选用下列任一形式，取其 stdout 作为 `hash`：

POSIX shell（locale 为 UTF-8 时 `printf` 直接输出 UTF-8 字节）：

```sh
printf '%s' '<完整分支名>' | sha1sum | cut -c1-6
```

**macOS 默认不带 `sha1sum`**，只有 `shasum`（默认算法即 SHA-1）；在 macOS 上或
`sha1sum: command not found` 时改用等价形式，不要卡在这里：

```sh
printf '%s' '<完整分支名>' | shasum | cut -c1-6
```

Windows PowerShell 5.1（显式取 UTF-8 字节，不依赖控制台代码页）：

```powershell
$bytes = [System.Text.Encoding]::UTF8.GetBytes('<完整分支名>')
$sha1 = [System.Security.Cryptography.SHA1]::Create()
try { $hashBytes = $sha1.ComputeHash($bytes) } finally { $sha1.Dispose() }
(-join ($hashBytes | ForEach-Object { $_.ToString('x2') })).Substring(0, 6)
```

`[System.Text.Encoding]::UTF8.GetBytes` 只挡住了控制台代码页这一层，**该片段必须
作为命令字符串直接传给 PowerShell，禁止先写成 `.ps1` 文件再运行**：若落成一个
没有 BOM 的脚本文件，Windows PowerShell 5.1 会按 ANSI 代码页解码文件内容，里面的
中文分支名字面量在读进来时就已经变成别的字符，`GetBytes` 拿到的自然是错的字节，
哈希**静默**变成另一个值——没有报错，只有对不上的文件名。本仓库的 `tests/*.ps1`
必须是 UTF-8 with BOM，正是同一个坑。

已验证的对照向量，用于自检**所选那条命令**（`sha1sum`、`shasum` 或上面的
PowerShell 形式）是否可用；对不上就说明取字节的方式错了，必须先修好再继续，
不得凭手算的值写文件：

| 完整分支名 | 文件名 |
|---|---|
| `feat/auth` | `feat-auth-3a9c55.md` |
| `feat-auth` | `feat-auth-f42474.md` |
| `功能/登录` | `功能-登录-9ff12b.md` |

分支现场与看板条目的 frontmatter 必须记录**完整分支名**与 **worktree 绝对路径**。
两者的校验强度不同，**不得混为一谈**：

- **完整分支名是硬一致性校验。** 文件名由分支名唯一决定，分支名对不上只可能是
  哈希碰撞，或文件被手工改名——两种情况下继续写入都会把本分支的现场覆盖到
  另一条线上。此时**停止写入该文件并报告**。
- **worktree 绝对路径只是信息字段。** `.handoff/*.md` 进 Git，会跟着仓库走：同事
  clone 到别的目录、`git worktree move`、仓库改名、换一台机器，都会让文件里记的
  绝对路径与当前路径不一致，而这些全是正常情况。若也按硬校验处理，除最初写入
  它的那台机器之外，所有人在每次调用时都会命中不一致而整体空转。因此路径不一致
  时**静默改写为当前 worktree 路径并继续执行**，只在报告中提一句。

差别的根据是这个字段进不进 Git、会不会随合法操作漂移：分支名是文件身份，跨机器
恒定；worktree 路径是本机事实，跨机器必然变化。用同一套强度处理这两者，等于把
「换台机器」误判成「文件被改名」。

写入任何一层之前必须先 `mkdir -p` 创建目录。空目录不进 Git，新建的 worktree 中
`.handoff/` 并不存在。

稳定层**不设全局更新时间戳**。1.x 顶部的 `> 更新时间` 行每次调用必变，两个分支
各运行一次即产生必然冲突。新鲜度改由 `git blame` 承担——它是逐行的，天然避开
全局戳的冲突，且无需任何写入端。不引入「最后核实」之类需要额外维护的标注：
任何只被读取、没有明确写入端的字段，最终都会变成执行者自行发挥的入口。
稳定层顶部改写 `<!-- sync:docs schema=2 -->` 作为版本标记。

稳定层仅在事实确实变化时才修改，禁止无意义重写。

## 信息淘汰

按判据可靠性分三级，判据越可靠动作越激进。三级机制**只产出淘汰决议，不自行写
文件**；决议与本次新内容在写入步骤合并后一次性落盘，避免同一文件被写两次。

### L1 客观过期：直接执行

判据均为 Git 或文件系统可回答的是非题。

| 对象 | 判据 | 动作 |
|---|---|---|
| 看板条目 | 分支已不在 `git branch -a --format='%(refname:short)'` 输出中 | 删除该条目文件 |
| 看板条目 | 分支仍在，但其 worktree 已不在 `git worktree list --porcelain` 中 | 不删，标注「无活跃 worktree」并转入 L2 |
| 分支现场 | 文件 frontmatter 记录的分支已不在 `git branch -a --format='%(refname:short)'` 输出中 | 决策提炼后删除，见下 |
| 分支现场 | 分支仍在，且已合并进主干（`git branch -a --merged <主干>`） | 决策提炼后删除，见下 |
| 分支现场 | 分支仍在、未合并，但其 `git log -1 --format=%cI <分支修订>` 超过 14 天 | 转入 L2 休眠流程，不直接删除 |
| 稳定层条目 | 引用的文件路径已不存在 | 就地标注 `⚠️ 路径已失效` |
| 常用命令 | 对应脚本或 target 已不存在 | 就地标注 `⚠️ 命令已失效` |

主干不可探测时跳过 merged 判据，保留分支存在性判据与时间判据，并在报告中说明。

**分支存在性判据必须把远端追踪分支算在内，`git branch` 不够。** `git branch`
只列本地分支。一份新 clone 里本地通常只有一个分支，若只看本地，`.handoff/` 里
同事那些**正在活跃开发**的分支现场会全部命中「分支已不在」，被提炼决策后删除。
这些文件进 Git，未提交前还能用 `git checkout -- .handoff` 找回，但用户只要跑一次
`git commit -am`，删除就被带进历史。因此判定一律用
`git branch -a --format='%(refname:short)'`（或等价地同时读 `refs/heads/*` 与
`refs/remotes/*`）。远端追踪分支的短名带 remote 前缀，比对时 `<分支名>` 与
`<remote>/<分支名>`（如 `feat/auth` 与 `origin/feat/auth`）任一命中即视为分支
仍存在。**本地没有、远端还有的分支绝不能判为已消失**——那通常只说明本人没有
checkout 过它，而不是这条线结束了。这条不得再收窄回只查本地。

**`git branch -a` 里会留下远端已删除分支的陈旧引用，这正是 tier 2 与 tier 3 也
必须认远端限定名的原因。** 远端删掉一条分支后，本地的
`refs/remotes/<remote>/<分支名>` 不会自动消失：普通 `git fetch` 不清理它，只有
`git fetch --prune`（或配置了 `fetch.prune`）才会。于是 GitHub 的默认流程
「推送 → 合并 → 删除远端分支」走完之后，在一份没有 prune 的 clone 里 tier 1 仍
看得到 `origin/<分支名>`，判定「分支还在」。此时若 tier 2 只查本地
（`git branch --merged <主干>` 不列远端追踪分支），tier 3 又拿裸分支名当修订
（本地 ref 已删，解析必然失败），三条判据会同时落空，`.handoff/` 从此只增不减，
正好是三级机制要防止的无限累积。因此 tier 2 用 `git branch -a --merged <主干>`，
tier 3 与 L2 的全部时间判据用下面定义的 `<分支修订>`。**这不是放宽 tier 1**：
tier 1 仍以「`git branch -a` 里还找不找得到」为准，本地没有、远端还有的分支依旧
不算消失；加固的是它之后的两条，不是它本身。

**`<分支修订>` 的解析顺序。** 时间判据要把分支名当 revision 传给 `git log`，而 Git
解析裸名时只查 `refs/heads/*`（以及 tag 等），**从不尝试
`refs/remotes/<remote>/<分支名>`**：对一条只剩远端追踪引用的分支，
`git log -1 --format=%cI <完整分支名>` 会直接以 exit 128 和
`fatal: ambiguous argument` 失败。因此按顺序解析：

1. 先试 `<完整分支名>`（取自现场文件或看板条目 frontmatter）；
2. 解析不到时，改试 tier 1 比对时在 `git branch -a` 输出里实际命中的那个
   `<remote>/<分支名>` 短名（如 `origin/feat/auth`）；
3. 两者都解析不到时，**该条时间判据视为未命中，本轮对该文件不做任何动作**。

候选是否可解析用 `git rev-parse --verify --quiet <候选>` 判定：可解析时输出对象名并
exit 0，不可解析时无输出并 exit 1，不会像 `git log` 那样打出 fatal 噪音。

第 3 条是安全底线：**修订解析失败绝不能被读成「长期无活动」**。时间判据问的是
「最后一次提交距今多久」，取不到这个时间就是取不到，不等于「很久没动过」。若让
`git log` 的失败沿用「超过 14 天 / 30 天」那条分支，一次临时的 ref 缺失就会把用户
的现场文件推向休眠甚至删除——把错误当成删除依据，方向恰好反了。不动作是可重复
的：下次运行若能解析，判据自然恢复生效。

时间判据统一用 `git log -1 --format=%cI <分支修订>`，L1 与 L2 的全部时间判据都用
这一形式。`--format=%cI` 只输出 ISO 8601 的**提交时间**：一来避免不带 `--format` 的
`git log -1` 把 commit subject 带进上下文——commit subject 属「敏感信息与证据读取
闸门」管辖，必须走同一本地调用的捕获与脱敏，判据不该在这里绕开它；二来消除
作者时间与提交时间的歧义。判据只需要一个日期，不需要标题。

**分支现场为什么需要三条判据。** 单靠 `git branch -a --merged` 有两个实测确认的
盲区，而它们恰好是 GitHub 的两项默认行为：**squash merge** 后主干上是全新提交，
功能分支 tip 永不可达，`--merged` 永不报告它，但现场文件已随 squash 进入主干；
**合并后删除分支**时 ref 最终消失（远端删除，本地再 prune），`--merged` 就再也
不列出它，孤儿文件却仍留在主干。两个盲区叠加会让 `.handoff/` 无限累积无法回收的
文件。因此以「分支是否还存在」为主判据，`--merged` 为次判据，时间判据兜底。判定用
的分支名取自现场文件 frontmatter 里的**完整分支名**，不从文件名反推——文件名经过
slug 化和哈希，不可逆；把它当 revision 传给 `git log` 时按上面的 `<分支修订>`
顺序解析。

**分支现场删除前必须先提炼决策，不限于已合并分支**：无论触发删除的是哪条路径——
分支已不在、已合并进主干，还是 tier 3 经 L2 休眠流程满 30 天——删除
`.handoff/` 现场文件前都必须先把该文件 `## 🧠 本分支决策` 中仍然成立的条目去重
并入稳定层 `## 🧠 长期决策与理由`。决策是长期资产，现场是易失状态，任何路径导致
的删除都不得绕过这一步，否则长期资产会随现场文件一起丢失。提炼后删除现场文件；
Git 历史保留完整内容，可用 `git log --all -- .handoff/<文件名>` 找回，且本 skill
不执行 commit，用户提交前必然看到 diff。

### L2 时间陈旧：降级

| 对象 | 判据 | 动作 |
|---|---|---|
| 看板条目 | 条目更新超过 14 天**且**该分支 `git log -1 --format=%cI <分支修订>` 也超过 14 天 | 在其 frontmatter 标记休眠并写入进入休眠时间 |
| 休眠的看板条目 | **进入休眠时间**距今超过 30 天**且**该分支 `git log -1 --format=%cI <分支修订>` 仍超过 30 天 | 删除该条目文件 |
| 分支现场 | 分支仍在、未合并，但其 `git log -1 --format=%cI <分支修订>` 超过 14 天（由 L1 的 tier 3 转入） | 在其 frontmatter 标记休眠并写入进入休眠时间 |
| 休眠的分支现场 | **进入休眠时间**距今超过 30 天**且**该分支 `git log -1 --format=%cI <分支修订>` 仍超过 30 天 | 决策提炼后删除，见上方「分支现场删除前必须先提炼决策」 |
| 任何休眠对象 | 该分支 `git log -1 --format=%cI <分支修订>` 在 14 天以内（线已重新活跃） | 清除休眠标记与进入休眠时间，退出休眠 |
| 任务看板 | `[x]` 已完成条目超过 15 条 | **保留最近 15 条，更早的全部合并为一行摘要** |

**休眠状态写在各自文件的 frontmatter 里，不存在独立的「休眠区」。** 协同看板是
每条线一个文件、聚合视图只在读取时现场渲染而不落盘，因此没有任何持久文件能
容纳一个专门的休眠区；把状态写进条目或文件自己的 frontmatter 是唯一可落盘的
表示方式。

**L2 必须覆盖分支现场，否则 L1 的 tier 3 落到空处。** tier 3 判定「分支仍在、
未合并、长期无活动」后要求「转入 L2 休眠流程」；若 L2 只处理看板条目，这条
路径既没有休眠起点可读，也没有对应的删除规则，执行者只能自行发明判据去删
用户的 `.handoff/` 文件。

**删除判据必须双条件，且必须有退出休眠的规则。** 只看进入休眠时间会误删活跃
分支：一条线静默 14 天被标记休眠，开发者第 20 天恢复开发并持续提交，到第 31
天时删除规则若只按时间戳触发，仍会删掉一个正在活跃开发的分支的现场文件——
而看板条目不进 Git，删除不可恢复。双条件是安全网：即使退出休眠的清除动作
因故没有执行，重新活跃的线也不会被误删。两者都要有，缺一不可：清除规则保持
状态干净，双条件兜住清除动作失效的情况。进入休眠本身就是双条件（条目时间 +
git 活动度），删除判据沿用同一形状。

「进入休眠时间」是独立字段，不能用「最后更新时间」代替：后者表示该线最后
一次真实活动，两者混用会丢失信息，且 30 天判据将无从计算。

进入休眠的两个条件必须同时满足。只看条目时间会误杀——用户可能在该分支持续
开发但未运行本 skill，叠加 Git 活动度后判定才准确。删除判据的双条件见上方
说明，形状相同但阈值改为 30 天。

时间一律取文件内记录的 ISO 8601 时间戳，**禁止使用文件 mtime**：`git checkout`
与创建 worktree 都会重写 mtime，据此判断会大面积误杀。

### L3 语义过期：只标注，不删除

适用于需要判断而非查证的情形，例如「下一步」中的事项看起来已完成、两处描述互相
矛盾。动作是就地改写为 `- [待核实] <原内容>`，**保留原文不删**，并在报告中列出。

这类判断可能出错，因此以「只标不删」限制其破坏面，把删除决定权留给用户；用户在
`git diff` 中一眼可见。

### 非 Git 项目的退化

**只维护稳定层 `HANDOFF.md` 这一层**，不创建 `.handoff/`，也不创建协同看板。
另外两层的文件名都由 `slug` 与 `hash` 构成，而两者的唯一输入是分支名；没有分支
就算不出文件名，`<common-dir>` 也不存在，这两层的路径根本无法构成。步骤 2 的
「写入三层」在此退化为**只写稳定层**，不是「先写再想办法定位」。

淘汰只保留三项判据与动作，它们都只查文件系统，与分支和时间无关：

| 对象 | 判据 | 动作 |
|---|---|---|
| 稳定层条目 | 引用的文件路径已不存在 | 就地标注 `⚠️ 路径已失效` |
| 常用命令 | 对应脚本或 target 已不存在 | 就地标注 `⚠️ 命令已失效` |
| 任意条目 | L3 语义过期 | 就地改写为 `- [待核实] <原内容>` |

被去掉的只有 L1 里依赖 Git 的三条（分支存在性、merged、worktree 存在性）与 L2
的全部时间判据——它们的输入全部来自 Git。**「常用命令对应脚本已不存在」不在
退化范围内**：它查的是文件是否存在，与分支和时间都无关，非 Git 项目一样能查、
一样需要查，不能因为「没有分支判据也没有时间判据」就把它一并砍掉。禁止执行
任何 Git 命令。

迁移锚点在此同样退化：**「主干探测失败」与「根本没有分支概念」是两回事，不得
按同一条规则处理。** 非 Git 项目永远不可能有主干分支，对它输出「稳定层拆分请在
主干分支运行一次」是在要求一件永远做不到的事，会让迁移永久卡死。因此非 Git
项目**直接在当前目录完成 1.x → 2.0 的稳定层改写**（只产出稳定层），并在报告中
说明「本项目非 Git，已按单层模式迁移」。「保守拒绝拆分」只适用于 Git 项目里
四级主干探测链全部失败的情况——那里存在多分支各拆一次导致稳定层分叉的风险，
而非 Git 项目连第二条线都不可能有，不存在该风险。

### 游离 HEAD 的退化

`git branch --show-current` 输出为空即处于游离 HEAD（rebase、bisect、CI 的
detached checkout 都会这样）。此时**没有分支名，也就没有分支身份**：`slug` 与
`hash` 的唯一输入缺失，分支现场与协同看板的文件名无法构成，与非 Git 项目同形。

因此**只写稳定层 `HANDOFF.md`**，跳过分支现场文件与协同看板条目，并在报告中明确
说明「当前为游离 HEAD，已跳过分支现场与看板条目」。但有一处与非 Git 项目不同：
1.x → 2.0 的稳定层拆分**不在游离 HEAD 上执行**，见「迁移锚点」；若稳定层尚未迁移
（顶部无 `<!-- sync:docs schema=2 -->`），本次不写任何文件，只在报告中说明原因。

**禁止用 commit SHA 顶替分支名去拼文件名。** 游离 HEAD 是临时状态，据此生成的文件
所对应的「分支」从来不存在：L1 的分支存在性判据下一轮就会判它是孤儿，而每次
checkout 到不同 commit 又会再新建一个——`.handoff/` 会被一批彼此无关、又永远回收
不掉的文件填满。宁可不写，也不写一个身份虚构的文件名。

**淘汰判定照常执行。** 本节只影响**写入**哪几层，不影响对已存在的现场文件与看板
条目做 L1/L2/L3 判定：那些判定的输入是各文件自己 frontmatter 里记录的完整分支名，
与当前 HEAD 是否游离无关。这里是 Git 仓库，Git 命令一律照常可用，与非 Git 项目
「禁止执行任何 Git 命令」不同，不要把两者混作一条规则。

## 老项目迁移（1.x → 2.0）

### 识别

| 痕迹 | 旧格式特征 | 处理 |
|---|---|---|
| `HANDOFF.md` | 不含 `<!-- sync:docs schema=2 -->` | 需要拆分 |
| `CLAUDE.md` | 含裸 `@HANDOFF.md` 行但无 `<!-- sync:docs start -->` | 升级为哨兵区块 |
| `AGENTS.md` | 已含 `<!-- sync:docs start -->` 与 `<!-- sync:docs end -->` | 幂等替换区块内容 |

### 迁移锚点

拆分只能发生一次。若各分支分别拆分，会产生互不相同的稳定层，造成严重冲突。

- 在主干分支：执行完整拆分。
- 在非主干分支：**非主干分支不修改 HANDOFF.md**，仅创建本分支现场文件与看板
  条目，并在报告中提示「稳定层拆分请在主干分支运行一次」。
- 主干无法探测时（Git 项目，四级探测链全部失败）：按非主干处理，**保守拒绝拆分**，
  并报告「无法确定主干分支，稳定层拆分已跳过」。拆分是一次性不可逆的结构变更，
  不确定时不做比做错好；若假定当前分支即主干，多个分支会各拆一次，正好造成本节
  要防止的稳定层分叉。
- 游离 HEAD（`git branch --show-current` 输出为空）：**保守拒绝拆分**，报告「当前
  为游离 HEAD，稳定层拆分请在主干分支运行一次」。这仍是 Git 项目，其它分支照样
  存在，在此拆分同样会造成稳定层分叉；且游离 HEAD 是临时状态，checkout 回主干后
  再运行一次即可满足，与非 Git 项目那个「永远无法满足的条件」不是一回事。
- 非 Git 项目：**没有分支这个概念，不适用上面三条**。见「非 Git 项目的退化」——
  直接完成稳定层改写，报告「本项目非 Git，已按单层模式迁移」。绝不能输出「请在
  主干分支运行一次」，那是一个永远无法满足的条件。

### 节归类

| 旧节 | 去向 |
|---|---|
| `## 概览` | 稳定层 `## 概览` |
| `## 📁 重要文件` | 稳定层 `## 📁 重要文件` |
| `## ⚠️ 注意事项 / 坑` | 稳定层 `## ⚠️ 注意事项 / 坑` |
| `## ▶️ 常用命令` | 稳定层 `## ▶️ 常用命令` |
| `## 🧠 关键决策与理由` | 稳定层 `## 🧠 长期决策与理由` |
| `## ✅ 已完成` | 分支现场 `## 📋 任务看板`，标记 `[x]` |
| `## 🔄 进行中` | 分支现场 `## 📋 任务看板`，标记 `[~]` |
| `## ⏭️ 下一步` | 分支现场 `## ⏭️ 下一步` |
| `> 更新时间：<时间>` | 删除 |

稳定层新增的 `## 🚀 运行现状` 与 `## 🔑 配置项清单` 由本次收集的证据填充；无法
确定的条目写「待补充」并在报告中列出。

迁移到分支现场的内容统一在顶部标注
`> 迁移自 1.x HANDOFF，未按分支归属核实`。1.x 在每个分支上都整体重写过，其中的
「已完成」可能混入其它分支的历史，不能默认属于当前分支。

## 敏感信息与证据读取闸门

该保护必须发生在任何原始 diff 正文或测试 stdout/stderr 进入任务上下文或
用户输出之前。默认只读取不含正文的安全元数据，包括 status、name-status、
stat 和 numstat。禁止把原始 diff 正文或测试 stdout/stderr 直接返回任务上下文
或用户。

需要内容时，必须在同一个本地命令或工具调用内捕获原始输出、完成敏感扫描与
脱敏，并且只返回脱敏结果。具体要求：

- 优先把原始输出只保留在该本地进程的内存中，不让子命令的 stdout/stderr
  直通外层工具结果。
- 若必须落盘，只能使用系统临时目录中的新建文件；原始输出只能留在该本地
  进程的内存或系统临时文件中；临时文件必须在 finally 中安全删除并做删除后
  断言。
- 返回前至少扫描 token、密码、私钥块、连接串、带凭据 URL、订阅链接、
  cookie、session、已知 secret/canary 标识和疑似高熵凭据；把整个敏感值替换为
  `[REDACTED]`，不能只遮盖一部分。
- 外层本地命令的 stdout/stderr 只能包含脱敏结果、exit code 和固定错误摘要；
  过滤器错误、子命令失败或清理失败时也不得回显原始内容。
- 在 Windows PowerShell 5.1 中不要依赖直接 `2>&1` 作为隔离边界；应使用
  `System.Diagnostics.Process` 重定向标准输出和错误，或使用等价的可靠本地捕获。
- 如果没有可靠的本地过滤能力，跳过原始内容读取，只基于安全元数据继续并
  明确报告限制；绝不降级为直接输出。

使用安全元数据、脱敏内容、旧交接、文件和对话作为证据时，仍要执行持久化前
筛查。不得把 token、密码、私钥、连接串、带凭据 URL、订阅链接、cookie 或
session 等敏感值写入 HANDOFF.md、其它文档或用户可见摘要。只记录存在敏感
配置、所在文件和需要人工处理，不记录或复述具体值；无法判断时按敏感信息
处理并脱敏。

不要为了生成交接主动打开与本次开发现场无关的 `.env`、私钥、凭据或订阅配置。
若安全元数据表明这类文件有改动，只记录路径和状态。若必要证据含疑似秘密，
后续内容只写脱敏占位和人工处理建议。

## 步骤 1：收集现场状态

Git 项目默认只运行并阅读下列安全元数据命令：

- `git branch --show-current`（当前分支名；输出为空即游离 HEAD）
- `git status --short`
- `git diff --name-status` 与 `git diff --staged --name-status`
- `git diff --stat` 与 `git diff --staged --stat`
- `git diff --numstat` 与 `git diff --staged --numstat`
- `git log --format="%h %ad" --date=short -15`

不要默认读取 content-bearing diff。若确有必要读取 diff 正文，按上面的闸门在
同一本地调用中捕获、扫描并只返回脱敏内容。需要运行或读取测试时同样禁止
stdout/stderr 直通：本地调用先捕获输出，只返回 exit code、脱敏后的测试摘要和
固定错误信息；无法可靠过滤时只记录“测试输出未读取”及其限制。
需要 commit subject 时，必须复用同一本地调用内捕获、扫描、脱敏的证据闸门。

再读取已存在的 `HANDOFF.md`，并结合当前对话中的已完成事项、关键决策和
下一步；读取和后续引用仍受上述闸门约束。若当前目录不是 Git 仓库，跳过全部
Git 命令，仅依据当前工作目录、对话和文件状态继续。

### 清点全部现场文件与看板条目

**必须做完这一步，步骤 1.5 才有输入。** 不只读当前分支那一份：

1. 枚举项目根 `.handoff/` 下的全部 `*.md`（目录不存在即为空集），逐个读取其
   frontmatter，记下**完整分支名**、worktree 路径、休眠标记与进入休眠时间。
2. 枚举 `<common-dir>/sync/lines/` 下的全部条目文件（目录不存在即为空集），逐个
   读取其 frontmatter，记下完整分支名、worktree 路径、一句话状态、**占用文件
   列表**、最后更新时间、休眠标记与进入休眠时间。
3. 读取 `git branch -a --format='%(refname:short)'` 与
   `git worktree list --porcelain`，作为分支存在性与 worktree 存在性的判定输入。

这三份清单是步骤 1.5 判定 L1/L2、以及步骤 5 做并行线冲突预警的唯一数据来源；
少读任何一份，对应的判定与预警都只能靠猜。frontmatter 属安全元数据，但其内容
仍受上面的敏感信息闸门约束。非 Git 项目跳过本小节的 2、3 两项与 `.handoff/`
枚举（这两层根本不存在，见「非 Git 项目的退化」）。

## 步骤 1.5：判定 L1/L2/L3 淘汰决议

**本步骤只做判断，不写任何文件。** 编号插在 1 与 2 之间而不合并进任何一方：
判定的输入是步骤 1 清点出的三份清单，输出是步骤 2 要执行的决议；两者一旦揉在
一起，就会出现「边判边写」，同一个文件被写两次。

逐项产出决议，不得跳过：

1. 对 `.handoff/` 的每个现场文件，按「信息淘汰 → L1」的三条分支现场判据依次
   判定（分支是否仍存在 → 是否已合并进主干 → 最后提交是否超过 14 天），命中
   tier 3 的转入 L2；已带休眠标记的按 L2 的删除判据与退出休眠判据判定。凡是把
   分支名当 revision 用的判据，一律按「信息淘汰 → L1」定义的 `<分支修订>` 顺序
   解析；两种形式都解析不到时该判据未命中，对该文件不产出任何决议。
2. 对 `<common-dir>/sync/lines/` 的每个条目，按 L1 的两条看板条目判据与 L2 的
   看板条目判据判定。
3. 对稳定层 `HANDOFF.md`，按 L1 判定引用路径与常用命令的存在性。
4. 对稳定层与当前分支现场（若存在），按 L3 判定语义过期项。
5. 对当前分支现场的任务看板，判定 `[x]` 条目是否超过 15 条需要收敛。

产出的决议按动作分四类，与步骤 2 第 2 步的四类一一对应：删除类、休眠标记类
（含清除标记）、就地标注类、任务看板收敛类。删除类必须同时记下**待提炼的决策
条目**，供步骤 2 并入稳定层。

**活跃线**在此一并确定：`<common-dir>/sync/lines/` 中同时满足「分支仍存在」
「未被 L2 标记休眠」「本轮未被判为删除」三条的条目所代表的线，即为活跃线。
步骤 5 的并行线冲突预警只比对活跃线的占用文件列表——已消失或休眠的线不构成
真实冲突，把它们算进去只会产生噪音预警。

非 Git 项目只执行上面的第 3、4 两项（见「非 Git 项目的退化」），并跳过活跃线
的确定：没有第二条线，也就没有冲突预警。

命中「预览」闸门时，本步骤照常执行——它本来就不写文件——判定结果全部列入报告。

## 步骤 2：执行淘汰决议、迁移并写入三层

本步骤执行的是**步骤 1.5 已经产出的决议**，不在此处重新判定。顺序执行，不得
只做其中一部分就结束——若只写三层，步骤 1.5 判定出的孤儿文件永不回收，
「老项目迁移」一节的规则也永远没有执行位：

1. **迁移**：若「老项目迁移」的识别表命中任一行，按该节规则完成迁移（含
   迁移锚点判断：主干才执行完整拆分；非 Git 项目按单层模式直接迁移）。
2. **执行淘汰决议**：按步骤 1.5 输出的四类动作执行——删除类（删除前必须先完成
   决策提炼并入稳定层，见「分支现场删除前必须先提炼决策」）；休眠标记类（在对应条目或
   文件自身的 frontmatter 写入休眠标记与进入休眠时间，或在线重新活跃时按
   L2 的退出休眠规则清除该标记）；就地标注类（`⚠️ 路径已失效`、
   `⚠️ 命令已失效`、`[待核实]`、「无活跃 worktree」等直接写在对应文件原位，
   不新建文件）；任务看板收敛类（`[x]` 已完成条目超过 15 条时合并为一行
   摘要）。
3. **写入三层**：把前两步的结果与本次新内容合并后一次性落盘。**非 Git 项目在此
   只写稳定层**——分支现场与协同看板的路径无法构成，见「非 Git 项目的退化」；
   **游离 HEAD 同样只写稳定层**，理由相同（没有分支名就算不出文件名），
   见「游离 HEAD 的退化」。

命中「预览」闸门时（见「调用与宿主闸门」），以上三步只在报告中列出拟执行
动作，不实际创建、修改或删除任何文件。

### 稳定层 `HANDOFF.md`

仅在事实确实变化时修改。顶部为 `<!-- sync:docs schema=2 -->`，无全局时间戳。

节结构：`## 概览`、`## 🚀 运行现状`、`## 🔑 配置项清单`、`## 📁 重要文件`、
`## 🧠 长期决策与理由`、`## ⚠️ 注意事项 / 坑`、`## ▶️ 常用命令`。某节确无内容时可
省略。同一事实只写一条，不得跨节重复。

`## 🚀 运行现状` 记录部署目标、启动方式、依赖的外部服务与端口；带凭据的 URL 必须
脱敏。`## 🔑 配置项清单` 只记录需要哪些环境变量或密钥、位于哪个文件、由谁提供，
**绝不记录配置项的值**。

### 分支现场 `.handoff/<slug>-<hash>.md`

整体重写。顶部写 `> 更新时间：<ISO 8601>` 与记录完整分支名、worktree 绝对
路径的 frontmatter；读取时按「三层交接布局」的差异化规则处理——分支名是硬一致性
校验，路径不一致时静默改写为当前路径并在报告中提一句。

「整体重写」不等于丢弃休眠字段：若该线仍处于休眠且仍无活动（未满足 L2 的
退出休眠条件），frontmatter 中的进入休眠时间字段必须原样保留到重写后的
文件里；若该线已按退出休眠规则重新活跃，重写时按该规则去掉该字段。是否
保留由 L2 的判据决定，不是「整体重写」本身决定。

节结构：`## 📋 任务看板`、`## 🧠 本分支决策`、`## ⏭️ 下一步`。

任务看板条目带稳定序号与状态标记：`[ ]` 待办、`[~]` 进行中、`[!]` 阻塞、
`[x]` 已完成。

### 协同看板 `<common-dir>/sync/lines/<slug>-<hash>.md`

只重写属于当前分支的那一份，**禁止写入汇总单文件**——两个 worktree 并发写同一
文件会导致先写方内容完全丢失。聚合视图在读取时现场渲染，不落盘。

「只重写属于当前分支的那一份」限制的是**改写其它线的条目内容**（一句话状态、
占用文件列表等实质内容），不限制按 L2 规则给其它线的条目追加或清除休眠标记：
L2 的休眠判据需要遍历全部线逐一评估，本就要读写非当前分支的条目文件，这与
「禁止写汇总单文件」不是同一件事——前者是单个条目文件内的字段增删，后者是
不得把多条线的信息聚合进一个文件。

单条内容写在该文件的 frontmatter：完整分支名、worktree 绝对路径、一句话
状态、占用文件列表、最后更新时间；完整分支名与 worktree 路径同样按「三层交接
布局」的差异化规则校验——分支名硬校验，路径不一致时静默更新。
条目被 L2 标记休眠时，在其自身 frontmatter 追加**进入休眠时间**字段（ISO 8601），
不存在独立的休眠区文件；该字段供 L2 的删除判据使用，不能用最后更新时间代替，
线重新活跃时按 L2 的退出休眠规则清除。
占用文件列表取自 `git diff --name-only` 与 `git diff --staged --name-only`，属安全
元数据。该文件虽不进 Git，仍受持久化前的敏感信息筛查约束。

## 步骤 4：刷新其它文档

逐项遵守：

- 日志/时间线型文档一律跳过去重。
- 只检查本次改动与对话实际涉及主题，不做全项目两两扫描。
- 建议类型仅为 `过时`、`可收敛`、`可合并`。
- 每项写路径、类型、原因、保留方、拟改内容和独有信息核对结果。
- 合并前保证不丢信息；受众不同默认只加指针。
- README、spec、HANDOFF、项目长期指令分别作为对应事实的权威出处。

识别建议时：

- `过时`：内容与当前已验证事实不符。
- `可收敛`：多个叙述型文档讲同一事实；保留权威出处，其它位置改为简短
  指针。
- `可合并`：一个叙述型文档基本是另一个的超集；仅在被合并方的全部独有
  信息已迁入保留方后合并。

日志型包括文件名或一级标题含 `log`、`changelog`、`journal`、`日志`、
`时间线`、`记录`、`ADR`、`decision`，或正文主体为带日期戳的时间序列。
受众不同的文档（如 README 面向用户、spec 面向开发者）不物理合并，
只建议添加指针，保留各自独立可读性。

### 应用方式

**Git 项目直接应用，不再要求确认编号。** 本 skill 从不执行 `git commit`，全部改动
停留在工作树，用户可用 `git diff` 复核、`git checkout` 撤销，Git 本身即安全网。

**非 Git 项目保留二次确认**：没有该安全网。修改前由同一本地调用捕获将修改文件的
**修改前 UTF-8 快照**；raw 快照只能留在进程内存或系统临时文件中，按闸门过滤后才可
返回。若发现疑似秘密且无法在不破坏原文的前提下安全修改，跳过该文件并请求人工
处理。

- 非 Git 项目禁止执行 Git 命令；应用后重新读取相关文件的 UTF-8 内容，原始前后
  内容仍留在同一本地调用内，只向用户返回脱敏差异摘要。

`/sync:docs 预览` 或 `$sync:docs 预览` 的只读语义见「调用与宿主闸门」；命中该
闸门时本节的应用动作同样不执行。

## 步骤 5：向用户汇报

用简体中文报告：

1. 实际创建或更新的文件路径（非 Git 项目与游离 HEAD 只有稳定层一条）
2. 当前宿主的续接载体
3. 本次淘汰明细：L1 删除项、L2 降级项、L3 标注为 `[待核实]` 的条目
4. **并行线冲突预警**：比对各活跃线（定义见步骤 1.5）的占用文件列表——该列表
   来自步骤 1「清点全部现场文件与看板条目」读到的条目 frontmatter——若两条线
   改动同一批文件，直接列出重合的文件与涉及的分支；非 Git 项目无此项
5. 若执行了迁移，说明迁移结果；若在非主干分支跳过了稳定层拆分，明确提示；
   非 Git 项目说明「已按单层模式迁移」
6. Git 项目附 `git diff --stat` 摘要；非 Git 项目摘要同一本地调用内 UTF-8 前后
   快照的脱敏比较结果，并明确全程未执行 Git 命令
7. 主干不可探测时，说明已跳过 merged 判据（分支存在性判据与时间判据仍已执行）
8. 若某个现场文件或看板条目记录的 worktree 路径与当前路径不一致而被静默更新，
   列出该文件与新旧路径
9. 若当前为游离 HEAD，说明已跳过分支现场与看板条目、只维护了稳定层；若稳定层
   因此连拆分也一并跳过，同时说明
10. 若某条时间判据因 `<分支修订>` 两种形式都解析不到而未命中，列出该文件与分支
    名，并说明本轮对它未做任何动作——不要让它看起来像「已确认无活动」

提示用户复核并自行决定是否提交。不执行 `git commit`。

## 常见错误

- 不把旧交接当作比实时 Git 更可信的事实。
- 不用 `git config init.defaultBranch` 探测主干。
- 不用文件 mtime 做时间判据。
- 不用只列本地分支的 `git branch` 判定分支是否还存在；必须用
  `git branch -a`，本地没有、远端还有的分支不是消失。
- 不因 `git branch -a` 里还有 `origin/<分支名>` 就以为远端分支一定还在；未 prune
  的陈旧引用同样会出现在那里，所以 merged 判据要用 `-a`，时间判据要能退到
  `<remote>/<分支名>`。
- 不把修订解析失败当成「长期无活动」；取不到提交时间就是取不到，本轮对该文件
  不做任何动作，绝不据此休眠或删除。
- 不用 `git rev-parse --abbrev-ref HEAD` 取当前分支名；游离 HEAD 时它返回字面量
  `HEAD`。用 `git branch --show-current`，输出为空即游离 HEAD。
- 不在游离 HEAD 上编造分支名，也不用 commit SHA 拼现场文件名；只写稳定层。
- 不在 macOS 上假定存在 `sha1sum`；那里用 `shasum`。
- 不把 PowerShell 哈希片段写进无 BOM 的 `.ps1` 再运行；必须作为命令字符串传入。
- 不心算或编造文件名哈希；必须用命令算 SHA-1。
- 不把 worktree 路径不一致当成停止写入的理由；那是信息字段，静默更新即可。
- 不在非 Git 项目创建 `.handoff/` 或协同看板，也不对它提示「请在主干分支运行」。
- 不把协同看板写成单个汇总文件。
- 不在非主干分支拆分稳定层。
- 不在稳定层写全局更新时间戳。
- 不直接运行会把原始 diff 或测试 stdout/stderr 返回任务上下文的命令。
- 不在过滤能力缺失或失败时降级输出原始内容。
- 不在 Codex 的 AGENTS 中写裸 `@HANDOFF.md`。
- 不扫描全项目做两两文档比较。
- 不在非 Git 项目中运行任何 Git 命令。
- 不读写 Claude Code 的 auto memory 目录。memory 是本机私有且不进 Git，Codex
  无对等物；由它承载长期偏好，本 skill 只承载项目现场，两者职责分离。
- 不自动 commit。
