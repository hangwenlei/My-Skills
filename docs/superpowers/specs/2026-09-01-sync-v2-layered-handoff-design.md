# sync 2.0：分层交接、并行线看板与信息淘汰设计

> 日期：2026-09-01
> 状态：已确认，待实施
> 影响插件：`sync`（1.2.0 → 2.0.0）

## 1. 背景与问题

`sync` 1.x 把整个开发现场写进项目根一个 `HANDOFF.md`，采用「快照式整体重写」。
实际使用中暴露三个问题：

1. **两阶段确认打断流程**。步骤 4.5 规定「初次调用列出清单后停止」，用户必须再输
   一次 `/sync:docs 应用 1,3` 才能完成文档刷新。
2. **多 worktree 并行时信息互相破坏**。用户以 git worktree / 分支并行开发，每条线
   都写同一路径的 `HANDOFF.md`，合并回主干时产生难解的 merge conflict；且任一条线
   都看不到其它线在做什么。
3. **信息只增不减**。旧条目没有淘汰机制，交接文档持续累积过时内容。

同时需要回答一个前置问题：Claude Code 的 auto memory 能否取代本插件。

## 2. 前置结论：auto memory 不能取代 sync

依据 Claude Code 官方文档核实：

| 维度 | auto memory | HANDOFF 体系 |
|---|---|---|
| 存储位置 | `~/.claude/projects/<项目>/memory/` | 项目内 |
| 是否进 Git | 否 | 是 |
| 可见范围 | 仅本机 Claude Code | Claude、Codex、人、其它机器 |
| 内容定位 | 偏好、纠正、代码推导不出的背景；**明确跳过可从代码推导的内容** | 现场快照：改了什么、进行中、下一步 |
| 容量 | `MEMORY.md` 仅加载前 200 行 / 25KB | 无硬限制 |
| 触发 | 模型自行判断，不保证每次保存 | 用户显式触发 |

关键否决理由：auto memory 是 machine-local 且不进 Git，**Codex 完全读不到**，
直接使本方案的「多 AI 协同信息沟通」目标落空。

**决策**：两者职责分离。auto memory 承载长期偏好与纠正，由 Claude 自行积累；
`sync` 不读写 memory 目录，避免双平台行为不一致。

## 3. 已验证的技术事实

本设计依赖的每条 git 行为均在 Windows + git bash 环境实测确认。

| # | 事实 | 用途 |
|---|---|---|
| T1 | `git rev-parse --show-toplevel` 在各 worktree 返回**各自的根** | 分支现场按 worktree 天然隔离 |
| T2 | `git rev-parse --path-format=absolute --git-common-dir` 在所有 worktree 返回**主仓库同一个 `.git`** | 协同看板的共享存放位置 |
| T3 | `.git/` 下自建目录不受 `git gc --prune=now` 影响，`git status` 不报告 | 看板存储安全 |
| T4 | `git branch --merged <主干>` 在**非主干 worktree 中同样可用**（refs 共享） | GC 的 L1 判据可靠 |
| T5 | `git config init.defaultBranch` 返回 `master`，而仓库真实主干为 `main` | **禁止**用它探测主干 |
| T6 | 孤儿现场文件来自**已合并**分支，而非已删除分支 | GC 判据方向 |
| T7 | `feat/auth` 与 `feat-auth` 的朴素 slug 均为 `feat-auth`，**碰撞真实存在** | 文件名必须加哈希 |
| T8 | 两个进程并发写同一文件，先写者内容**完全丢失** | 看板必须分文件 |
| T9 | 空目录不进 Git，新建 worktree 中 `.handoff/` 不存在 | 写入前必须 `mkdir -p` |
| T10 | **squash merge 后** `git branch --merged` **不报告**该分支，但其现场文件已进入主干 | 孤儿判据不能只依赖 `--merged` |
| T11 | **分支删除后** `git branch --merged` 不再列出它，孤儿文件仍留在主干 | 需以「分支是否存在」为主判据 |
| T12 | 远端删除分支后，`origin/<name>` 在普通 `git fetch` 后**仍留在** `git branch -a` 中，只有 `fetch --prune` 才清理 | tier 1 不能只信 `-a` 的输出；tier 2、tier 3 必须能处理远端限定名 |
| T13 | 裸分支名对只有 `refs/remotes/` 引用的分支**不解析**，`git log -1 <name>` 退出 128 `fatal: ambiguous argument` | 时间判据须回退到 `<remote>/<name>`，均不解析时 no-op，失败绝不读作「无活动」 |
| T14 | detached HEAD 时 `git branch --show-current` 输出**空串但 exit 0**；`git rev-parse --abbrev-ref HEAD` 输出字面量 `HEAD` | 取分支名只用前者，以输出是否为空判定 detached，禁用后者 |

T5、T6、T7、T8 均推翻了朴素实现，是本设计存在的直接原因。

## 4. 架构：三层分离

按「变动频率」和「归属范围」切分。

```
项目根/
├── HANDOFF.md                    [进 Git] 稳定层
│     <!-- sync:docs schema=2 -->
│     概览 / 运行现状 / 配置项清单 / 重要文件 / 长期决策 / 坑 / 常用命令
│     无全局时间戳
│
├── .handoff/                     [进 Git] 分支现场
│   ├── feat-auth-a3f2c1.md       任务看板 / 本分支决策 / 下一步 / 更新时间
│   └── feat-billing-7d91e0.md
│
└── <git-common-dir>/sync/lines/  [不进 Git] 协同看板
    ├── feat-auth-a3f2c1.md
    └── feat-billing-7d91e0.md
```

### 4.1 稳定层 `HANDOFF.md`

承载跨分支都成立的事实，变动慢。由 `CLAUDE.md` 的 `@HANDOFF.md` 静态导入，
因此必须保持精简。

节结构：

- `## 概览`
- `## 🚀 运行现状`：部署目标、启动方式、依赖的外部服务、端口
- `## 🔑 配置项清单`：需要哪些环境变量/密钥、位于哪个文件、由谁提供
- `## 📁 重要文件`
- `## 🧠 长期决策与理由`
- `## ⚠️ 注意事项 / 坑`
- `## ▶️ 常用命令`

**不设全局更新时间戳。** 1.x 顶部的 `> 更新时间：<时间>` 行每次 sync 必变，
两个分支各跑一次即 100% 冲突。新鲜度改由 `git blame` 承担——它是逐行的，天然
避开了全局戳的冲突，且无需任何写入端。不引入「最后核实」之类需要额外维护的
标注：任何只被读取、没有明确写入端的字段，最终都会变成执行者自行发挥的入口。

`<!-- sync:docs schema=2 -->` 采用 HTML 注释形式，恰好利用 Claude Code 的行为：
块级 HTML 注释在注入上下文前被剥离，因此该标记不消耗用户上下文；而 skill 用
Read 工具直接读文件时注释仍可见，判据不受影响。

**写入约束**：仅当事实确实变化时才改稳定层。禁止无意义重写。

### 4.2 分支现场 `.handoff/<slug>-<hash>.md`

承载易失的执行状态，只由所属分支写入。

- 当前分支名用 `git branch --show-current` 取得（依据 T14）。输出为空即 detached HEAD：
  此时没有分支身份，**只写稳定层**，跳过分支现场与看板条目并报告。不要从 commit SHA
  造文件名——detached 是瞬态，会留下「分支」从不存在、永远无法回收的文件
- **哈希必须用命令算，禁止心算**。语言模型无法可靠计算 SHA-1，心算结果跨次不一致，
  每次运行都会生成新文件名。POSIX 用 `printf '%s' '<分支名>' | sha1sum | cut -c1-6`
  （macOS 默认无 `sha1sum`，用 `shasum`）；PowerShell 用 `[System.Text.Encoding]::UTF8.GetBytes`
  显式取 UTF-8 字节再 SHA-1，且必须作为命令串传入而非写进无 BOM 的 `.ps1`。用已验证
  向量自检所选命令：`feat/auth`→`3a9c55`、`feat-auth`→`f42474`、`功能/登录`→`9ff12b`
- `slug`：分支名将 `/ \ : * ? " < > |` 替换为 `-`
- `hash`：**完整分支名的 UTF-8 字节**做 SHA-1，取前 6 位十六进制，解决 T7 的碰撞。
  必须显式指定 UTF-8，不得依赖平台默认编码，否则含中文的分支名在 Windows
  PowerShell 与 git bash 下会算出不同哈希
- frontmatter 记录完整分支名与 worktree 路径。**两者校验强度不同**：完整分支名是
  硬一致性校验——与文件名反推不符即意味着哈希碰撞或手工改名，停止写入该文件并报告；
  worktree 路径只是信息字段——`.handoff/` 进 Git 而路径是本机事实，同事 clone 到
  不同路径、`git worktree move`、换机器都会使其失配，若把它也当硬校验，除作者本人外
  每个协作者的每次调用都会因「路径不一致」空转。失配时静默改写为当前路径并在报告中
  提一句

节结构：

- `## 📋 任务看板`：条目带状态标记 `[ ]` 待办 / `[~]` 进行中 / `[!]` 阻塞 / `[x]` 已完成，带稳定序号
- `## 🧠 本分支决策`
- `## ⏭️ 下一步`
- 顶部 `> 更新时间：<ISO 8601>`

因文件名含分支标识，两个分支产生的是不同文件，**merge 时不构成冲突**。

### 4.3 协同看板 `<git-common-dir>/sync/lines/<slug>-<hash>.md`

每条线只写自己那一份（依据 T8，禁止单文件汇总）。聚合视图在读取时现场渲染，
不落盘，避免再引入一个需要并发写的文件。

单条内容：

- 完整分支名、worktree 绝对路径
- 一句话状态
- **占用文件列表**：来自 `git diff --name-only` 与 `git diff --staged --name-only`
- 最后更新时间（ISO 8601）
- 进入休眠时间（ISO 8601，仅休眠条目有此字段，供 L2 的 30 天删除判据使用）

**冲突预警**：sync 运行时比对各活跃线的占用文件列表，若两条线改动同一批文件，
在报告中直接预警。这是「多 AI 协同」最实际的价值点。

依据 T3，该目录不受 `git gc` 与 `git status` 影响。依据 T9，写入前必须 `mkdir -p`。

## 5. 信息淘汰：三级机制

按**判据可靠性**分级，判据越可靠，动作越激进。

三级机制**只产出淘汰决议，不自行写文件**。决议与本次新内容在流程第 5 步合并后
一次性落盘，避免同一文件在一次调用中被写入两次。

### 5.1 L1 客观过期 —— 直接执行

判据均为 git 或文件系统可回答的是非题。

| 对象 | 判据 | 动作 |
|---|---|---|
| 看板条目 | 分支已不在 `git branch --format` 输出中 | 删除该条目文件 |
| 看板条目 | 分支仍在，但其 worktree 已不在 `git worktree list --porcelain` 中 | **不删**，标注「无活跃 worktree」后转入 L2 时间判据 |
| 分支现场 | 文件 frontmatter 记录的分支**已不在** `git branch -a --format='%(refname:short)'` 输出中，裸名与 `<remote>/<名>` 任一命中即视为存在（依据 T10、T12） | 决策提炼后删除，见 5.4 |
| 分支现场 | 分支仍在，且**已合并进主干**（`git branch -a --merged <主干>`，依据 T4、T6、T12） | 决策提炼后删除，见 5.4 |
| 分支现场 | 分支仍在、未合并，但其 `git log -1` 超过 14 天（依据 T11） | 转入 L2 休眠流程，不直接删除 |

**分支现场为什么需要三条判据。** 单靠 `git branch --merged` 有两个实测确认的盲区
（T10、T11），而它们恰好是 GitHub 的两项默认行为：

- **squash merge**：主干上是一个全新提交，功能分支的 tip 永远不可达，
  `git branch --merged` 永不报告它，但该分支的现场文件已随 squash 进入主干。
- **合并后删除分支**（GitHub "delete branch on merge" 默认开启）：分支 ref 一旦消失，
  `git branch --merged` 就再也不会列出它，而孤儿文件仍留在主干。

两个盲区叠加的结果是：绝大多数真实项目的 `.handoff/` 会无限累积无法回收的孤儿文件，
恰好使本设计要解决的问题原样复现。因此以「分支是否还存在」为主判据（覆盖两种删分支
路径），`--merged` 为次判据（覆盖合并后保留分支），时间判据兜底（覆盖 squash 后
保留分支）。三条合起来无盲区。

判定所依据的分支名取自现场文件 frontmatter 中记录的**完整分支名**，不从文件名反推
——文件名经过 slug 化和哈希，不可逆。

**远端追踪引用会陈旧，所以三级判据都必须能处理远端限定名（T12、T13）。** 分支在远端
删除后，`origin/<name>` 在普通 `git fetch` 后仍留在 `git branch -a` 里，只有
`fetch --prune` 才清理。若 tier 1 只信 `-a` 的输出而 tier 2、tier 3 又只处理裸名，
则「推送 → 合并 → 远端删除」这条 GitHub 默认流程会让三级全部落空，`.handoff/` 回到
无限累积。因此 tier 2 用 `git branch -a --merged`；凡以分支名作 revision 参数的判据
（tier 3 与全部 L2 时间判据），解析顺序为：裸名 → `<remote>/<分支名>` → 均不解析则
该判据**不满足**（no-op）。查找失败绝不能读作「无近期活动」，否则一次命令错误就会把
文件送上删除路径。
| 稳定层条目 | 引用的文件路径已不存在 | 就地标注 `⚠️ 路径已失效` |
| 常用命令 | 对应脚本 / make target 已不存在 | 就地标注 `⚠️ 命令已失效` |

### 5.2 L2 时间陈旧 —— 降级

| 对象 | 判据 | 动作 |
|---|---|---|
| 看板条目 | 条目更新 > 14 天 **且** 该分支 `git log -1` 也 > 14 天 | 在其 frontmatter 标记休眠并写入进入休眠时间 |
| 休眠的看板条目 | 进入休眠时间距今 > 30 天 **且** 该分支 `git log -1` 仍 > 30 天 | 删除该条目文件 |
| 分支现场 | 分支仍在、未合并，但其 `git log -1` > 14 天（由 5.1 的 tier 3 转入） | 在其 frontmatter 标记休眠并写入进入休眠时间 |
| 休眠的分支现场 | 进入休眠时间距今 > 30 天 **且** 该分支 `git log -1` 仍 > 30 天 | 决策提炼后删除，见 5.4 |
| **任何休眠对象** | **该分支 `git log -1` 在 14 天以内（线已重新活跃）** | **清除休眠标记与进入休眠时间，退出休眠** |
| 分支现场任务看板 | `[x]` 已完成条目数 > 15 | **保留最近 15 条，更早的全部合并为一行摘要** |

**删除判据必须双条件，且必须有退出休眠的规则。** 只看进入休眠时间会误删活跃分支：
一条线静默 14 天被标记休眠，开发者第 20 天恢复开发并持续提交，到第 31 天时删除规则
仍会纯按时间戳触发，删掉一个正在活跃开发的分支的现场文件——而看板条目不进 Git，
删除不可恢复。双条件是安全网：即使退出休眠的清除动作因故没有执行，重新活跃的线也
不会被删。两者都要有：清除规则保持状态干净，双条件兜住清除失效的情况。

进入休眠本身就是双条件（条目时间 + git 活动度），删除判据沿用同一形状。

**休眠状态写在各自文件的 frontmatter 里，不存在独立的「休眠区」。** 协同看板是每条线
一个文件、聚合视图只在读取时渲染而不落盘（4.3），因此没有任何持久文件能容纳一个
「休眠区」；把状态写进条目自己的 frontmatter 是唯一可落盘的表示方式。

**L2 必须覆盖分支现场，否则 5.1 的 tier 3 落到空处。** tier 3 判定「分支仍在、未合并、
长期无活动」后要求「转入 L2 休眠流程」；若 L2 只处理看板条目，这条路径既没有休眠起点
可读，也没有对应的删除规则，执行者只能自行发明判据去删用户的 `.handoff/` 文件。

「进入休眠时间」是独立字段，不能用「最后更新时间」代替：后者表示该线最后一次真实
活动，两者混用会丢失信息，且 30 天判据将无从计算。

「条目更新时间」一律取**文件内记录的 ISO 8601 时间戳**，不得使用文件 mtime：
`git checkout` 与 worktree 创建都会重写 mtime，据此判断会大面积误杀。

**「且」是必要的**：只看条目时间会误杀——用户在该分支持续开发但未运行 sync。
叠加 git 活动度后判定才准确。

阈值 N=14 / M=30 / K=15 为固定值，不提供配置项（YAGNI）。

### 5.3 L3 语义过期 —— 只标注，不删除

适用于需要模型判断的情形：

- 「下一步」中的事项看起来已经完成
- 两处描述互相矛盾

**动作**：就地改写为 `- [待核实] <原内容>`，**保留原文不删**，并在报告中列出。

理由：模型在这类判断上会出错。保留原文使一条指令跑完不打断用户，同时把
删除决定权留给用户——`git diff` 中一眼可见。

### 5.4 已合并分支的决策提炼

删除已合并分支的现场文件前，先将其 `## 🧠 本分支决策` 中仍然成立的条目并入
稳定层 `## 🧠 长期决策与理由`，去重后写入。

理由：决策是长期资产，现场是易失状态，两者应分开对待。直接删除会丢失
「为什么选 X 不选 Y」这类无法从代码恢复的信息。

提炼后删除现场文件。Git 历史保留完整内容，可用
`git log --all -- .handoff/<文件名>` 找回；且 sync 不执行 commit，
用户在提交前必然看到 diff。

### 5.5 主干分支探测

依据 T5，禁止使用 `git config init.defaultBranch`。按以下优先级：

1. `git symbolic-ref --quiet refs/remotes/origin/HEAD`
2. `origin/main` 或 `origin/master` 的存在性
3. 本地 `main` 或 `master` 的存在性
4. 均不可得 → **跳过 merged 判据（tier 2）**，保留分支存在性判据与时间判据，并在
   报告中说明。只有 merged 判据需要主干；若连分支存在性判据一并跳过，孤儿回收
   整体失效

## 6. 执行流程

`/sync:docs`（Claude Code）或 `$sync:docs`（Codex）单次调用完成全部工作。

```
1. 定位      项目根(T1) / 主干分支(5.5) / common dir(T2) / 当前分支
2. 收集      安全元数据：status、name-status、stat、numstat、log
             ── 敏感信息闸门原样保留，默认不读 raw diff 正文 ──
3. 迁移检测  见第 7 节
4. GC        L1 → L2 → L3 依次评估，**只产出淘汰决议，不直接落盘**
5. 落盘      **执行淘汰决议并写入三层，是同一个步骤**：先执行决议中的删除
             （删除前完成决策提炼并入稳定层）与休眠标记，再写稳定层
             （仅当事实变化）/ 分支现场（重写）/ 本线看板条目（重写）。
             第 3 步判定需要迁移时，迁移也在本步执行。
             步骤标题若只说「写入」，严格照步骤执行的执行者会写完就走，
             L1 判定出的孤儿文件永不回收，迁移规则也永远没有执行位。
6. 续接配置  CLAUDE.md 哨兵区块（Claude）/ AGENTS.md 哨兵区块（Codex）
7. 文档刷新  直接应用，不再要求确认编号
8. 报告      改了什么 + git diff --stat + GC 清理明细 + 并行线冲突预警
```

### 6.1 取消两阶段确认

删除 1.x 步骤 4.5 的「初次调用列出清单后停止」。

**理由**：`sync` 从不执行 `git commit`，全部改动停留在工作树，`git diff` 可查、
`git checkout` 可撤。git 本身已是安全网，事前确认属于冗余保护。

**例外**：非 Git 项目没有该安全网，**保留二次确认**。

### 6.2 预览开关

`/sync:docs 预览` 输出全部拟执行动作（含迁移计划、GC 明细）但不写任何文件。
供用户在老项目首次运行前先行核对。

**该闸门必须在流程第 1 步之前判定，且作用于全流程。** 预览是只读承诺，而 L1 的删除
在写入步骤就已落盘；若把开关的语义定义放在靠后的步骤里，按编号顺序执行的执行者会先
删掉 `.handoff/` 现场文件与看板条目，之后才读到「不写任何文件」这句话——一次声称
只读的调用已经销毁了用户数据。参数闸门与宿主闸门同级，写在调用入口处。

### 6.3 敏感信息闸门

1.x 的闸门**完整保留**，包括：默认只读安全元数据、raw diff 与测试输出必须在
同一本地调用内完成捕获与脱敏、过滤能力缺失时不降级输出、持久化前筛查。

新增内容的约束：

- `## 🚀 运行现状`：可写部署目标、启动命令、依赖服务、端口；带凭据的 URL 必须脱敏
- `## 🔑 配置项清单`：**只记 key 名、所在文件、由谁提供，绝不记 value**
- 看板的占用文件列表：仅为文件路径，属安全元数据
- 看板文件虽不进 Git，仍受持久化前筛查约束

## 7. 老项目迁移（1.x → 2.0）

### 7.1 识别判据

| 痕迹 | 旧格式特征 | 处理 |
|---|---|---|
| `HANDOFF.md` | 无 `<!-- sync:docs schema=2 -->` 标记 | 需拆分 |
| `CLAUDE.md` | 有裸 `@HANDOFF.md` 行但无 `<!-- sync:docs start -->` | 升级为哨兵区块 |
| `AGENTS.md` | 已有 `<!-- sync:docs start/end -->` | 幂等替换区块内容 |

### 7.2 迁移锚点锁定主干

**拆分只能发生一次。** 若各分支分别拆分，会产生互不相同的稳定层，造成严重冲突。

- **在主干分支**：执行完整拆分。
- **在非主干分支**：**不修改 `HANDOFF.md`**，仅创建本分支现场文件与看板条目，
  并在报告中提示「稳定层拆分请在主干分支运行一次」。
- **主干无法探测时**（5.5 的四级链全部失败）：按非主干处理，**保守拒绝拆分**，
  并报告「无法确定主干分支，稳定层拆分已跳过」。拆分是一次性不可逆的结构变更，
  不确定时不做比做错好；若此时假定当前分支即主干，多个分支会各拆一次，正好造成
  本节要防止的稳定层分叉。

该规则使非主干分支立即获得新功能，又不污染稳定层。

### 7.3 节归类映射

| 旧节 | 去向 |
|---|---|
| `## 概览` | 稳定层 `## 概览` |
| `## 📁 重要文件` | 稳定层 `## 📁 重要文件` |
| `## ⚠️ 注意事项 / 坑` | 稳定层 `## ⚠️ 注意事项 / 坑` |
| `## ▶️ 常用命令` | 稳定层 `## ▶️ 常用命令` |
| `## 🧠 关键决策与理由` | 稳定层 `## 🧠 长期决策与理由` |
| `## ✅ 已完成` | 分支现场 `## 📋 任务看板`，标记为 `[x]` |
| `## 🔄 进行中` | 分支现场 `## 📋 任务看板`，标记为 `[~]` |
| `## ⏭️ 下一步` | 分支现场 `## ⏭️ 下一步` |
| `> 更新时间：<时间>` | 删除（见 4.1） |

稳定层新增的 `## 🚀 运行现状` 与 `## 🔑 配置项清单` 由本次收集的证据填充；
无法确定时写「待补充」并在报告中列出。

迁移到分支现场的内容统一标注：
`> 迁移自 1.x HANDOFF，未按分支归属核实`。

理由：旧版在每个分支上都整体重写过，其中的「已完成」可能混入其它分支的历史，
不能默认它属于当前分支。

### 7.4 续接区块升级

Claude Code 的 `CLAUDE.md`：

```markdown
<!-- sync:docs start -->
@HANDOFF.md

## 开发现场续接

当前分支的执行现场在 `.handoff/` 下，取其 frontmatter 记录的完整分支名与当前分支
一致的那一个文件，开始任务时一并读取。并行线看板位于仓库 common dir 的
`sync/lines/`（不进 Git）。
把交接文档作为线索；若与实时 Git、测试或文件状态冲突，以实时证据为准。
<!-- sync:docs end -->
```

续接文案**不能**说「与当前分支同名的文件」：实际文件名是 `<slug>-<hash>.md`，经过
slug 化与哈希后不可反推（4.2）。多分支仓库的 `.handoff/` 下有多个文件，按「同名」
去找会读进另一条分支的现场，污染下一次写入。必须按 frontmatter 中的完整分支名匹配。

`@HANDOFF.md` 必须独占一行且**不得被反引号包裹**，否则 Claude Code 不会导入。
区块内其它路径一律用反引号包裹，防止被误当作导入指令。

Codex 的 `AGENTS.md` 沿用现有哨兵机制替换区块内容，**不得写裸 `@HANDOFF.md`**。

哨兵校验沿用 1.x 规则：开始与结束哨兵各恰好一次且顺序正确才替换；单边、重复
或逆序时停止修改该文件并报告。

**一处必须写明的例外**：两个哨兵都不存在时，通用规则是「追加」，但若此时文件中
存在 1.x 遗留的裸 `@HANDOFF.md` 独占行，必须**替换该行**而不是追加。否则旧的裸
导入行会永远留在哨兵区块之外——后续幂等运行只认哨兵区块，永远清理不到它——同时
区块内又有一个导入行，`CLAUDE.md` 出现两个 `@HANDOFF.md` 且状态不收敛。
替换优先于追加。

## 9. 非 Git 项目

无分支、无 common dir，退化处理：

- 仅维护单个 `HANDOFF.md`，不创建 `.handoff/` 与看板
- GC 仅保留「引用路径存在性」检查与 L3 标注，无 L1 分支判据、无 L2 时间判据
- **保留二次确认**（无 git 安全网）
- 沿用 1.x 的修改前 UTF-8 快照比对机制
- 禁止执行任何 git 命令

## 10. 已知限制

如实记录，不隐藏：

1. **分支现场无法被 `@` 静态导入**。`CLAUDE.md` 的 `@` 导入在会话启动时静态展开，
   无法指向「当前分支对应的那一份」。只能依赖续接区块的自然语言指令，属**软保证**。
   硬保证需要 SessionStart hook，用户已明确排除自动 hook 方案。
2. **稳定层冲突未归零**，只是概率大幅降低。跨分支同时修改运行现状等内容仍会冲突。
3. **协同看板不跨机器**。存放于 `.git/` 且不进 Git，仅覆盖同一台机器上的多 worktree
   协同，不覆盖多人多机协同。
4. **L3 语义判断依赖模型**，可能误标。设计上以「只标不删」限制其破坏面。
5. **本机未安装 Claude CLI**，Claude runtime 实测仍无法执行，沿用静态校验加
   发布包结构验证，不得表述为实机通过。
6. **tier 2 的 `<主干>` 参数尚无解析规则**（2.0.1 待修）。主干探测链第 1/2 级从远端
   返回裸名（如 `main`），若本地没有同名分支，`git branch -a --merged main` 报
   `fatal: malformed object name`、exit 128，tier 2 静默失效。两位实施者先后独立发现
   同一根源；`algo` section 的现有夹具即可复现。失败方向是「不删」，属安全侧，故未
   阻断发布。修法与 5.1 已定的 `<分支修订>` 解析同形：裸名 → `<remote>/<主干>` →
   均不解析则跳过 tier 2 并报告。
7. **两套测试证明「文本没有退化」，不证明「指令可被正确执行」。** `gc-scenarios.ps1`
   的 scenario section 用 PowerShell 重写判据后在真实仓库上验证裁决，是目前最接近
   执行的验证，但 skill 本身一次也没被执行过。真正的端到端验证（造仓库 → 跑 skill
   → 比对文件树）仍是下一轮目标，且本仓库自身的 1.x→2.0 迁移（计划 Task 9）按裁决
   留到发布并升级本机插件之后。

## 13. 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 单文件 + 分支哨兵区块 | 仍是同一文件，merge 冲突未解决，且文件随分支数线性膨胀，`@` 导入会把所有分支现场载入上下文 |
| 现场全部移出 Git（放 common dir） | 等于把 sync 降级为 memory，丢弃进 Git、跨平台、跨机器这一唯一优势 |
| `.gitattributes` 设 union merge driver | 对 markdown 产生重复行，结果不可读 |
| sync 代写 auto memory | memory 不进 Git 且 Codex 无对等物，会造成双平台行为不一致，并与 Claude 自动积累的内容重复 |
| SessionEnd / PreCompact hook 自动触发 | 用户明确排除：会在不知情时改文件、花费 token |
| L2 阈值可配置 | YAGNI，固定 14/30/15 |
